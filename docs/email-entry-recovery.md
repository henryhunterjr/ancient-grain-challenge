## Entrant behavior

The existing-entry section offers **Email me a sign-in link** as well as the existing private-code sign-in. Every valid email request receives the same message: “If that email belongs to an entry, a sign-in link will arrive shortly. Check your inbox and spam folder. Links expire after 15 minutes.” This message does not confirm that an entry exists or that email delivery succeeded. Requests do not create entries or newsletter subscriptions.

For exactly one matching normalized email, the backend emails a private, random, single-use link. Opening it does not consume it: the entrant must click **Continue to recover my entry**. The server atomically consumes the credential and returns that entry's original code and first name. The page displays the code, then requires **Use my recovered entry for [name]**. A different or changed browser session requires an explicit switch confirmation. Recovery never rotates, shortens or invalidates old entry codes, changes points, or grants prize eligibility.

The **Copy code** button reports success only when a clipboard operation succeeds. Otherwise it selects the code and gives manual-copy instructions. Newly issued registration codes appear immediately, before progress loading finishes. If localStorage cannot save the code, it remains visible and usable in memory on that page with a clear warning to copy it before leaving. A failed progress load offers Retry loading my entry instead of a second registration form.

Pending Muse results retain the existing nonsecret seven-day pending-result contract, expiry and clear/cancel behavior. Recovery does not alter pending data or save a score automatically. After sign-in, **Return to record my pending score** leads to the existing explicit identity-confirmed save. On a different device/browser, the old device's pending result is not transferred by email; return there, or use the original nonsecret results link. Blocked persistent storage cannot survive closing the page: the visible private code is the recovery path.

Expired, invalid, already used or interrupted redemption offers a fresh-link request. Refreshing the recovery page also requires reopening the original email link or requesting another because its credential is stripped from the URL immediately and never persisted. If the server consumes a credential but the response is lost, requesting a new link safely recovers the same unchanged entry.

## Architecture and access

This revision uses a dedicated PostgreSQL login through Supabase's shared transaction pooler, with node-postgres 8.23.1 pinned in package.json and its lockfile. It removes custom JWT minting, signing-secret handling and recovery-specific publishable-key configuration. The existing entrant UUID code remains the identity; no parallel Supabase Auth user system is created.

Initial read-only inspection found 28 entrants, zero normalized duplicate emails, zero Auth users and zero Edge Functions. Henry later confirmed bakinggreatbread.com is Verified in Resend, approved noreply@bakinggreatbread.com, and reported saving a new domain-restricted Sending key, FROM and ENABLED=false in Vercel Production. Their private values were not read. Recipe Pantry and its keys remain untouched.

The applied reviewed migration created agc_entry_recovery_worker with NOLOGIN and no password. It has NOINHERIT, no superuser, database/role creation, replication or RLS bypass, no privileged role memberships, no table access or application-schema CREATE privilege, and a backend connection limit of 10. It receives recovery-schema USAGE and EXECUTE on exactly three private recovery application functions. No membership is granted to authenticator. The role is activated only by a separately approved owner-private password setup.

Read-only metadata showed three public application functions still granting EXECUTE to PUBLIC: register with ten parameters, winners(), and admin_draw with four parameters. Each already grants execution explicitly to anon, authenticated, service_role and its owner. The migration verifies that exact snapshot, removes only these three PUBLIC grants and preserves every explicit grant. This prevents the new login inheriting unrelated application functions without changing current frontend/admin API access or function bodies. Missing explicit grants, unexpected PUBLIC application functions, missing expected PUBLIC grants, ambiguous emails or an existing worker role abort for review. The legacy email/name-only recover RPC remains revoked. No registration, drawing or eligibility policy changes.

The worker can execute only three application functions; normal PostgreSQL built-ins and PUBLIC CONNECT/TEMP privileges are not a SQL statement sandbox. Future application functions must revoke default PUBLIC execution before deployment. A compromised worker password is still sensitive: these three functions can recover entry credentials, and it must stay server-only.

The private RLS-enabled schema stores only credential SHA-256 hashes, entrant IDs, creation/expiry/use times, and durable HMAC-hashed rate counters. New recovery tables contain no raw credentials, email addresses or IPs. Existing entrants already retain their registration email. Ambiguous normalized email matches fail closed both before migration and at runtime. No entrant merge or duplication is attempted.

Limits are database-serialized: requests 100/hour globally, 10/15 minutes per IP, 3/hour per email and a 60-second email cooldown; redemption 300/hour globally and 30/15 minutes per IP. Unknown addresses consume identical counters. Atomic conditional UPDATE permits only one redemption across concurrent server instances. Fixed windows can burst around boundaries; the cooldown remains. Initial global caps need owner review for expected traffic and can reduce availability during a coordinated flood.

## Transport, TLS and transaction guarantees

The app fixes username to agc_entry_recovery_worker.pmhytaaajbhzyldmxmzb, database to postgres, and transaction-pooler port to 6543. AGC_RECOVERY_DB_HOST must be an actual shared-pooler hostname ending in .pooler.supabase.com, taken from Connect. Only a separate dedicated password is accepted; no connection URL, configurable username, JWT, signing secret, service-role key or database-owner credential is used by this transport.

Each warm API instance reuses a pool with max=1, acquisition/connect timeout 750 ms, idle expiry 10 seconds and lifetime 60 seconds. Changed configuration closes the previous pool. TLS requires certificate trust and hostname verification, rejectUnauthorized=true, and minimum TLS 1.2. The actual pooler requires Supabase's independently obtained public root CA PEM in AGC_RECOVERY_DB_CA; insecure fallback is forbidden. Credential-free Node and installed Windows psql checks verified trust and hostname on ports 5432 and 6543. Node negotiated TLS 1.3 and psql stopped at no password supplied. Wrong hostname and unrelated CA were rejected. No live login has been completed.

Every allowlisted parameterized function call runs BEGIN, transaction-local statement/lock limits, the private function and COMMIT under one default 2-second deadline. Statement and lock limits are 1.2 and 0.8 seconds. A result is returned only after COMMIT confirmation. Any error/timeout destroys the connection and rolls back uncommitted work instead of reusing an aborted transaction. No named prepared statements, query pipelining, session state, cursors or session-level advisory locks are used; the request/redeem locks are transaction-level. This follows Supabase's documented transaction-pooler protocol constraints, but actual managed-pooler authentication/cache behavior remains a post-approval check.

Both APIs require POST, the fixed registry Origin, JSON, bounded payloads, exact allowed fields and a validated platform IP header. Issued links are fixed to https://challenge.bakinggreatbread.com/recover-entry#r=<random credential>, never an entrant code or caller-chosen destination. The fragment is immediately removed; redemption is in an HTTPS POST body, and GET/scanners do not consume it. The page has local assets only, no analytics, no-referrer/no-store/noindex and restrictive CSP. Private values/errors/provider responses are not logged. Valid requests share a generic response and nominal 4.5-second deadline, with bounded provider/database operations. Failed delivery revokes the credential when the database is reachable.

Expired links and rate rows are purged on the next valid issue request once expiry/last activity is over 24 hours old. This is opportunistic cleanup, not a scheduled deletion guarantee; hashes can remain during inactivity. Rollback retains inaccessible private hashes/counters. Providers necessarily receive recipient and email body. Owner review must keep API bodies, Authorization headers and provider payloads out of logs/analytics and confirm tracking is off. Do not alter shared Resend settings affecting Recipe Pantry without separate review. Mailbox control can recover an entry; existing long-lived codes remain bearer credentials.

## Rotation, revocation and rollback

Before planned rotation, disable delivery under owner approval, repeat the private helper with a new dedicated password and renewed expiry, update only the worker password, deploy and verify fresh authentication before enabling. Record the renewal deadline privately. Password changes alone do not end established sessions; the app retires its own connections after 60 seconds, while managed pooler caching must be checked during the approved live setup.

For suspected compromise, the reviewed database/disable-email-recovery.sql removes password/LOGIN and revokes all three function grants, blocking even an authenticated session. Do not rely on waiting for expiry. Restore only those three grants after owner incident review and credential replacement. Leaked long-lived entrant codes need separate owner handling; they are never rotated automatically here.

Rollback disables delivery first and restores the preceding reviewed frontend/API deployment, then applies database/rollback-email-entry-recovery.sql. It removes the worker functions/role/access and restores precisely the three original PUBLIC grants. Original entrants, codes, scores, claims and sessions remain unchanged. Private hashes/counters and the inaccessible rate helper remain. Re-enabling requires a reviewed follow-up migration because the private schema is retained; blindly rerunning CREATE SCHEMA fails.
