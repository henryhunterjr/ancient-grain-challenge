# Email entry recovery — draft implementation and publication review

Status: development and draft PR only. Based on production commit `552e1eac16897957d1aa3ae08314a863f44c163c`. No production migration, credential provisioning, auth configuration, actual email delivery, entrant modification or deployment is authorized by this draft. Admin passcode and private-code visibility in admin/CSV stay unchanged.

## Entrant behavior

The existing-entry section offers **Email me a sign-in link** as well as the existing private-code sign-in. Every valid email request receives the same message: “If that email belongs to an entry, a sign-in link will arrive shortly. Check your inbox and spam folder. Links expire after 15 minutes.” This message does not confirm that an entry exists or that email delivery succeeded. Requests do not create entries or newsletter subscriptions.

For exactly one matching normalized email, the backend emails a private, random, single-use link. Opening it does not consume it: the entrant must click **Continue to recover my entry**. The server atomically consumes the credential and returns that entry's original code and first name. The page displays the code, then requires **Use my recovered entry for [name]**. A different or changed browser session requires an explicit switch confirmation. Recovery never rotates, shortens or invalidates old entry codes, changes points, or grants prize eligibility.

The **Copy code** button reports success only when a clipboard operation succeeds. Otherwise it selects the code and gives manual-copy instructions. Newly issued registration codes appear immediately, before progress loading finishes. If localStorage cannot save the code, it remains visible and usable in memory on that page with a clear warning to copy it before leaving. A failed progress load offers Retry loading my entry instead of a second registration form.

Pending Muse results retain the existing nonsecret seven-day pending-result contract, expiry and clear/cancel behavior. Recovery does not alter pending data or save a score automatically. After sign-in, **Return to record my pending score** leads to the existing explicit identity-confirmed save. On a different device/browser, the old device's pending result is not transferred by email; return there, or use the original nonsecret results link. Blocked persistent storage cannot survive closing the page: the visible private code is the recovery path.

Expired, invalid, already used or interrupted redemption offers a fresh-link request. Refreshing the recovery page also requires reopening the original email link or requesting another because its credential is stripped from the URL immediately and never persisted. If the server consumes a credential but the response is lost, requesting a new link safely recovers the same unchanged entry.

## Architecture and access

This is a server-side bridge to the existing UUID bearer-code identity, rather than a second Supabase Auth user system. Read-only inspection found 28 entrant rows, zero normalized duplicate emails, zero Supabase Auth users, zero Edge Functions, and no Vercel application environment variables. The existing transactional-email provider and managed Supabase SMTP settings could not be established from safe metadata; they must not be assumed configured or absent.

`api/recovery/request.js` and `api/recovery/redeem.js` use the built-in Node transport in `server/recovery.cjs`. The supplied mail adapter uses Resend; Henry must approve that provider or request a reviewed adapter for his existing provider. Tests mock email exclusively.

The new `agc_entry_recovery_worker` database role can execute the three new privileged recovery RPCs. It has no direct entrant/table access, no schema access to private recovery storage, and no grant of `anon`, `authenticated` or `service_role`. Existing functions granted to PostgreSQL `PUBLIC` remain reachable as they already are for callers; this role adds only the dedicated recovery privileges. The former email/name-only `recover` RPC must remain revoked. The browser receives no worker/provider credential. The backend deliberately refuses `service_role` credentials and fails closed without all configured prerequisites.

The un-applied migration creates a private RLS-enabled schema containing credential SHA-256 hashes, entrant IDs, creation/expiry/use times, and durable HMAC-hashed rate counters. Raw recovery credentials, email addresses and IPs are not stored in those new tables. Entrant records already retain email for registration. Issuance fails closed for ambiguous normalized email matches both in the migration preflight and at runtime. No data merge is attempted.

Issuance uses database-serialized limits: 100 valid requests/hour globally, 10/15 minutes per IP, 3/hour per normalized email, and a 60-second email cooldown. Unknown addresses consume the same counters. Redemption is limited to 300/hour globally and 30/15 minutes per IP. Global serialization and atomic conditional UPDATE make concurrent issuance/redemption safe across server instances; only one redemption can return an entry. Fixed windows can allow bursts around boundaries; the email cooldown still applies. This initial global limit trades abuse resistance for availability during a coordinated request flood and needs owner review for expected traffic.

The Vercel platform IP header is preferred and validated. Both APIs require POST, the fixed registry Origin, JSON, bounded input and exact permitted fields. Only `https://challenge.bakinggreatbread.com/recover-entry#r=<random credential>` is issued; callers cannot choose a destination. No entry code appears in this link. The fragment is removed before any API call; credential redemption travels in the HTTPS POST body. GET/link scanners do not redeem. The receiving page uses only local assets, no analytics, no-referrer, no-store, noindex and a restrictive CSP. API code does not log credentials, emails, IPs, provider responses or private errors. Valid request responses use the same generic body and nominal 4.5-second deadline; provider/RPC timeouts are bounded. Failed delivery attempts revoke the issued credential when the database is reachable.

Expired links and rate rows are purged on the next valid issuance request once their expiry/last activity is more than 24 hours old. This is opportunistic cleanup, not a scheduled 24-hour deletion guarantee. During inactivity, private hashes can remain until the next request or separately approved cleanup. Rollback deliberately retains inaccessible private hashes/counters.

Email providers necessarily receive the recipient and private email body. Owner configuration must disable click/open tracking for the sending domain and keep request bodies out of Vercel/Supabase log drains and analytics. Do not install logging middleware that captures either API body, Authorization headers or provider payloads. Mailbox access can recover an entry; old long-lived entry codes remain bearer credentials under the existing model.

## Owner prerequisites before publication

1. Review and approve the migration, new role/grant to `authenticator`, sender/provider choice, limits, retention and email recovery's access implications. Recheck normalized duplicates and actual privileges immediately before applying the new migration. Do not reapply prior challenge migrations or any earlier cleanup.
2. Confirm an approved way to provision a finite-expiry JWT with role exactly `agc_entry_recovery_worker`, accepted by this project's Data API. Supabase documents custom role impersonation with a valid signed JWT, but the project's current signing configuration has not been verified. A signing authority must remain outside this application and chat; put only the scoped worker JWT in Vercel. Do not fetch or put the project JWT signing secret, service-role key or database admin password in this app. If a scoped JWT cannot be issued under the current signing setup, stop for a reviewed alternative transport rather than broadening privileges. Schedule owner renewal before the worker JWT expires; expiry disables recovery while old-code sign-in continues.
3. Approve Resend or a compatible reviewed provider adapter. Verify a transactional sending domain/address with the provider, configure its required DNS records, disable link/open tracking, and provision a restricted sending API key. No provider account, domain, DNS, key or SMTP configuration has been changed by this work.
4. Enter values privately in the correct Vercel project's Production environment. `.env.example` lists blank names only: `AGC_RECOVERY_DATABASE_TOKEN` (scoped JWT), `AGC_RECOVERY_PUBLISHABLE_KEY` (public Data API key), `AGC_RECOVERY_RESEND_KEY` (restricted sender key), `AGC_RECOVERY_FROM` (verified sender), and `AGC_RECOVERY_RATE_PEPPER` (owner-generated random secret, at least 32 characters). Keep `AGC_RECOVERY_ENABLED=false` during setup. Never paste secrets into chat, commit them, copy broad environment dumps, or put them in browser variables. Do not change the admin passcode.
5. After explicit publication approval, apply only `20261008211000_email_entry_recovery.sql`, verify worker/anonymous grants, deploy the reviewed commit, then set `AGC_RECOVERY_ENABLED=true` and redeploy under owner control. The feature branch has automatic deployments disabled. No configured provider/worker integration or live email test has been claimed.
6. Separately authorize one controlled owner-email end-to-end check, including inbox delivery, link expiry/reuse, unchanged original code/progress, old-code access, pending-score return, and private logging behavior. This is an owner test, not a real-entrant signup, subscription, score submission or drawing. Until then, mail delivery, actual project custom-role JWT acceptance and the Vercel production API build remain unverified deployment prerequisites.

The API's fixed Origin intentionally prevents running a credential-bearing recovery flow on arbitrary preview domains. A future protected staging test needs an independently reviewed staging origin, isolated database and sender configuration; do not aim a preview at production entrants.

## Rollback and validation

Disable `AGC_RECOVERY_ENABLED` first; restore the preceding reviewed frontend/API deployment; remove or revoke the worker/provider credentials privately; then apply the reviewed `database/rollback-email-entry-recovery.sql`. It drops the three new public RPCs, revokes role membership/access and drops the worker role. Existing entries, original codes, scores, claims and sessions stay intact. The private hash/counter schema is retained without exposed endpoints. Re-enabling after rollback needs a reviewed follow-up migration because that schema remains; blindly rerunning the original create-schema migration will fail.

Validation uses synthetic local entries, mocked provider/API calls and disposable PostgreSQL 17 only:

- Node API tests cover generic responses, normalized email, fixed-origin links, hash-only RPC payloads, provider errors/revocation, bounded requests, POST/Origin/content type/IP validation, tampered payloads, confirmed code return and refusal of broad service-role configuration.
- Local SQL tests cover access isolation, duplicate preflight/runtime rejection, cooldown/email/IP/global limits, expiry, reuse, revocation, unchanged original entry/claims and rollback. Ten concurrent issuance sessions and ten concurrent redemption sessions each return exactly one success.
- Chrome tests cover the existing Muse/lesson/registration regressions plus email requests, interrupted/failed/expired recovery, private credential removal, explicit cross-entry/session switching, pending-result preservation, double clicks, clipboard failure and immediate code visibility with blocked storage. Mobile, desktop and dark screenshots are captured under ignored `test-output/`.

Run `node tests/email-recovery.test.cjs`, `python tests/run-email-recovery.py` (disposable local PostgreSQL on loopback port 55439 only), and `node node_modules/@playwright/test/cli.js test`. On Windows use explicit executable paths. The local preview serves raw checked-in files and mocks email endpoints in tests; it is not a configured email service.

Final local result: **6 Node API tests passed; 24 Chrome tests passed; PostgreSQL security, concurrent issuance/redemption, duplicate, expiry, limits and rollback checks passed.** Screenshots were visually checked at 320/393px, desktop, and dark mode. Production mail delivery and production API deployment remain untested.
